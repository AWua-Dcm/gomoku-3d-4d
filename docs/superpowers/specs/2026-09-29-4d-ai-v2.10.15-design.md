## 一、目标与验收

### 用户要什么

1. **四维人机要会用转动**：通过旋转打散对方即将成型的棋；通过旋转让自己成四子或其他有利阵型；在**合适的时候**才转。
2. **棋盘规格上限从 50 改成 30**（`BoardLimits`：8 ≤ N ≤ 30）。
3. **三维主要提升极限档；四维每一档都要提升。**
4. **极限档（ultra）显著变强**，不为省时间牺牲棋力。
3. **要理解玩家每一步在干嘛**：如果自己来替玩家走，会下在哪里从而获胜。
4. **起始界面**：拉到「极限」时，拉条上移几像素、下方出小字「思考时间可能会明显增长」，**不影响其他按键的位置**。
5. 版本号 `v2.10.15`。

### 验收标准（用户口径）

- 配对自对局（第 2k 局与第 2k+1 局**共享开局种子、只对调颜色**）：**新人机 vs 旧人机，新人机胜率 ≥ 70%**。
- 主战场 **四维 8³、转动冷却 3 手**；三维 15³ 同法量一遍，只要求**不回归**。
- **测量台自检**：旧 vs 旧的对照组必须**恰好 50.0%**，否则这批数字全部作废（见 `tests/ai.test.mjs:742-756` 的方法论，v2.10.14 已踩过一次坑）。
- 现有 9 步离线检查全绿（`_verify/run-all.sh`）。

### 明确不在本次范围

- **真·自对弈机器学习**（策略/价值网络、TD 学习）。理由：本工程刻意零依赖、单文件、跑在浏览器里，训练不现实，且会破坏「零依赖」这个前提。**可行且会做的是配对自对弈 A/B 调参**——这个仓库一直在用（`ai.test.mjs` 注释里那些 40/120 局的实测就是）。
- 三维的转动（三维棋盘上转动根本不存在）。

| 四维转动 | 根节点独立启发式：`brk`（拆形）/ `build`（调形） | `aiRotationProbe` [index.html:4557](../../../Web_Gomoku3D/index.html#L4557) |
| 对手建模 | 仅体现为叶子评估里对方那一项乘 `AI_EVAL_W`=0.5 | `aiEvalLeaf` [index.html:4704](../../../Web_Gomoku3D/index.html#L4704) |

### 三个具体缺口

**缺口 1：转动从不和落子比价。**
`brk` 只要找到「转完对方低于活三」就**无条件返回**（[index.html:5187-5189](../../../Web_Gomoku3D/index.html#L5187-L5189)），从不问「老实去堵是不是更好」。`build` 只在落子那手做不出活三时才试（[index.html:5206-5213](../../../Web_Gomoku3D/index.html#L5206-L5213)）。两者都用**档位阈值**而非真实估值判断好坏。这正是实测注释里那句「对方一点威胁都没有时它照样转、转完对方原地点了同一格」的结构性原因。

**缺口 2：每个节点的排序开销与搜索规模不匹配。**
搜索实际只展开 `branch`=4 个候选，却对**全部**候选（15³ 中盘约 235 个）逐个做 13 方向 × 双方的完整威胁扫描（`aiOrderKey` → `aiThreatAt` ×2 → `countRun` ×2 + 滑窗）。这是每节点的绝对大头，也是深度上不去的直接原因。

**缺口 3：看不见对手的强制胜。**
叶子评估把对方的最好一手打个 0.5 折是**常数近似**，不是事实。对手真正有连续冲四（VCF）取胜时，「折半」远远不够——引擎会走进一个必败局面而评估值看着还不错。

## 三、设计

`BoardLimits.Max` 由 50 改成 30。**范围只有 `BoardLimits` 这一处定义**（[index.html:3231](../../../Web_Gomoku3D/index.html#L3231)），其余地方都从它现算或由测试对拍，但**波及面仍然比看上去大**：

| `README.md` / `Web_Gomoku3D/README.md` | 表格里的 `8 – 50`、以及一批「50³」的性能叙述 |
| `tests/online-http.test.mjs` | `/8 – 50/` 这条正则 |

| `AI_SEARCH_DROP` [index.html:4290](../../../Web_Gomoku3D/index.html#L4290) | 阈值是按 50³ 反推的，30³ 最大候选数小一个量级 → 重新实测后重定 |

**这一条要单独提交**，且必须在那次提交上跑一次完整的 `run-all.sh` —— 它是纯机械改动，混进 AI 改动里会让「棋力变化」和「规格变化」两件事没法分开归因。

**顺带的好处**：30³ = 27,000 格，比 50³ 的 125,000 格小 4.6 倍。50³ 密集局面（单手 200ms）这个最坏情况**整个消失**，3.2 / 3.3 的收益更好兑现。

### 3.1 威胁空间搜索：VCF → VCF ∪ VCT，并且双向

**攻方**（`aiVct`）：把现有 `aiVcf` 的强制手集合从「冲四」扩到「冲四 ∪ 活三」。

- 冲四：对方应手**唯一**（堵成五点），分支因子 = 我有几个冲四。
- 活三：对方应手**不唯一**（2~3 个堵点）——**必须穷举对方应手**，只试一个就会报出假胜着，让电脑走出一手送死棋。这是本次新代码里**最危险的地方**。
- 为了压住分支：每个 VCT 节点最多尝试 `M` 个活三着法，每个着法穷举对方应手（上限 `D` 个）。**初值 `M`=6、`D`=4**，进 `AI_PARAMS` 当旋钮，实测再调。冲四那一支仍然只走唯一应手，保持原样。
- **穷举的是「对方所有应手」，不是「对方最好的应手」**——后者不构成证明。若某个应手超过上限 `D` 被截断，**这一支必须判为未知（不算胜）**，宁可不报胜着，也不许报假胜着。
- **长连规则**照旧：受限方走出长连是判负，算杀链里任何一步都用 `judge` 判，不用「数够 5 个就赢」的写法（见 `aiOutcomeAt` 的注释）。

**守方**（复用同一段，换 `attacker`）：根节点对**排序前 K 个**候选各问一次「我走完这手之后，对手有没有强制胜」。有 → 这一手是必败着，剔除。存活下来的再比大小。

> **为什么是根节点而不是叶子**：仓库实测过「算杀进叶子」——同档 A/B 40 局正好 50.0%，**一分棋力都不多**，单手耗时翻倍（见 [index.html:4843-4846](../../../Web_Gomoku3D/index.html#L4843-L4846)）。这个结论不违背，本次**不把 VCT 放进叶子**。

### 3.2 Zobrist 置换表

**键** = 棋盘逐格 ⊕ 出子权 ⊕ 受限身份 ⊕ 冷却进度 ⊕ `tune` 参数签名。

三个本作特有的坑，必须处理：

1. **转动会批量置换棋子**。键不能只支持「落/撤一子」，得支持「整层置换」：逐格 XOR 掉旧值、XOR 上新值（O(n²)，可忽略），并在 `probeRotate` 的还原路径上同样维护。
2. **冷却手数不在盘面上**。`placementsSinceLastRotation` 决定了 `canRotate`，它不进棋盘，所以**必须进键**；否则两个「盘面相同、能不能转不同」的局面会互认。
3. **`tune` 参数必须一起进键**（`winLength` / `branch` / 双方受限身份）。不同档位、不同规则下同一个盘面的值不同，混用会读到脏表。

**生命周期**：每手 `aiChooseMove` 开头用**代数戳**重置（和现有的 `aiSeenBits` / `aiSeenStamp` 完全同一套写法，[index.html:4361](../../../Web_Gomoku3D/index.html#L4361)）。这样：
- 确定性契约（同局面 + 同种子 → 同动作）**零风险**——整个计算仍然是纯确定性的；
- 不会出现「跨手复用了不同参数下的表项」这类只能在特定对局里偶发的脏 bug。

跨手持久化暂不做（收益不确定，风险明确）。

**表的规模**：50³ = 125000 格 × 3 态 × 4 字节 = 1.5MB 的 `Int32Array`，按需按尺寸惰性分配。表项数组本身是定长的（2 的幂），满了就**按代数戳整片作废**，不做复杂淘汰。

### 3.3 走法生成与排序优化

**两段式**：

1. **廉价键**（对所有候选，O(候选数)）：邻域内已占格数 + **中心加权**（`-w × 谢比雪夫中心距`）。
2. 取廉价键前 `3 × branch` 个，**只对这批**算完整的 `aiOrderKey`，再按既有的 `aiSearchCompare` 全序排序。

**根节点不做预筛**——那一层最贵也最要紧，预筛丢掉根节点的正确着法代价最大。内层才筛。

**中心加权只进排序键，不进评估分数**。`aiCenterDist` 现在的注释写着「只当 tie-break 用，绝不进分数」，这条**保持不变**：中心加权是「同等威胁时先看中间」，不是「中间本身值分」。

另外把 `aiThreatAt` 热循环里的 `board.inBounds()` / `board.get()` 函数调用改成直接扁平下标 + 预计算步长（越界靠逐轴夹取，**绝不走扁平下标加减**——那条注释里的坑照旧）。

**安全网**：这一项是**唯一**可能悄悄改变搜索看到哪些候选的改动。改完必须配对 A/B 对比，棋力掉了就退回全量排序。

### 3.4 四维转动进根候选池

**分两档处理**：

**（a）语义修复——所有档位生效，零额外成本。**
`brk` 不再无条件返回：它产出的转动候选要和「老实去堵」的那一手**在同一个尺度上比**。`build` 同理。这一条修的是逻辑，不是性能。

**（b）极限 / 极高两档：转动由真实搜索估值。**
根节点把**落子**和**转动**放进同一个候选池，各自用同一段搜索估值，谁高走谁。

- 转动候选：只取「层里有子」的层；极限档**全枚举**（8³ = 3 轴 × 8 层 × 3 次 = 72 个，空层预筛掉）。四维默认 8³，全枚举成本可接受。
- **保留两条既有安全绳**（测试钉着它们，[ai.test.mjs:333-377](../../../Web_Gomoku3D/tests/ai.test.mjs#L333-L377)）：
  - 转完不许给对方留活三以上；
  - 硬规则链（能赢必赢 / 必堵必堵）永远排在转动前面，**任何档位都不许跳过**。
- 低 / 中 / 高 三档保留现在的廉价启发式 + （a）的语义修复。理由：它们本来就该快，而且**梯子要留梯子**——低档必须有搜索档赢不了的强度。

### 3.5 极高档与极限档的档位差

现在的实测档位差里，**极限打极高只有 52.5%**（[ai.test.mjs:793-799](../../../Web_Gomoku3D/tests/ai.test.mjs#L793-L799)），落在噪声里——极限档比极高档只多了「根节点算杀」和「够便宜多算一层」。

本次把差距拉开。**但档位改动是分模式的**（用户口径：**三维主要提升极限档；四维每一档都提升**）：

| | 三维 low/medium/high | 三维 xhigh | 三维 ultra | 四维每一档 |
|---|---|---|---|---|
| 走法生成两段式 | 否 | 否 | **开** | **开** |
| Zobrist 置换表 | 否 | 否 | **开** | **开** |
| 搜索深度 | 不变 | 不变（5） | 5 → 9 | 各档照旧加深 |
| 迭代加深 | 否 | 否 | 开，层数上限提高 | 照旧 |
| 算杀 | 否 | VCF（根节点） | **VCF ∪ VCT**（根节点） | VCT 进高档 |
| 对手强制胜过滤 | 否 | 否 | **开** | **开** |
| 转动品质 | 不适用（三维无转动） | 不适用 | 不适用 | **3.4（a）语义修复 +（b）搜索比价** |

**三维的梯子必须保住**：除了极限档，三维其余档位**一个参数都不动**。理由是极限打极高现在只有 52.5%（落在噪声里），而低/中/高的档差是健康的（87.5% / 85.0% / 77.5%）—— 动它们只会把梯子压平。

**四维不一样**：用户要的是"四维每一档都要提升"，所以 3.4 的转动改进**四维全档生效**（低/中/高也改，因为它们转得好不好直接决定这一档像不像会下四维）。四维各档的搜索深度按 3.5 的加深幅度各自上浮。

深度仍取奇数（`ai.test.mjs:433` 有断言钉着，实测偶数深度打不过浅一层的奇数深度）。

### 3.6 界面上界与测试口径

按已确认的选择：**低 / 中 / 高 / 极高保留墙钟断言；极限档删掉墙钟断言，改用「扫过多少候选点」的计数预算封顶**。这与仓库既有的「用计数器不用墙钟，免得慢机器上随机变红」做法一致（[ai.test.mjs:810-811](../../../Web_Gomoku3D/tests/ai.test.mjs#L810-L811)）。

**基线实测（2026-09-29，`node Web_Gomoku3D/tests/ai.test.mjs`，156 项全绿，8m37s）：**

```
15³ 中盘（40 子）：候选 235，judge 705，用时 3ms，动作 place
50³ 密集（5000 子）：候选 7500，用时 19ms
50³ 密集 · xhigh：用时 201ms，算杀 0 格
50³ 密集 · ultra：用时 210ms，算杀 1 格
```

两条结论，都影响本节的做法：

1. **「15³ 中盘 ultra ≤500ms」这条墙钟断言近乎空转。** `judge 705 = 3 × 235` 说明它走的判断链是第 1 步（235）+ 第 2 步（235×2 = 470），**在第 3 步「对方能赢就去堵」就返回了，一步搜索都没跑**。这个随机 40 子局面（5×5×5 盒子里塞 40 颗）对手必有一步成五点。所以真正的耗时证据只有 50³ 密集那条和真实对局。删它之前先确认这一点，别把它当成"极限档很快"的证据。
2. **50³ 密集局面的 200ms 几乎全花在「给 7500 个候选逐个算完整排序键」上**，不在搜索、也不在算杀（xhigh 算杀 0 格、ultra 1 格）。深度早就被 `AI_SEARCH_DROP` 降到 2 了，5 个节点。这正好是对 3.3 两段式优化最有利的证据：廉价键过一遍 7500 个，再对 3×branch = 12 个算完整键，这一处就能把 200ms 压到十毫秒量级。

具体：
- 删掉 `ai.test.mjs` 里对 ultra 的两条墙钟断言（15³ 中盘 500ms、50³ 密集 2000ms）——**保留这两处对其余档位的断言**。
- 给极限档加一条**计数上界断言**：单手的候选扫描数不超过一个实测反推的值。定法：先量出改版后 50³ 密集局面单手「扫过的候选点」的**最大值**，上界取实测最大值的 1.5 倍写死；数字进 commit message，以后谁把预算删了就红。
- 50³ 密集局面下 ultra 的计数预算必须**仍然封顶**——否则「手机上点一下卡十秒」会回来。这条预算由 `AI_VCF_BUDGET`（按点记账）和 `AI_ID_NODES`（按节点记账）两个计数器共同承担，本次要给后者也改成按点记账，两者才好加总。

### 3.7 起始界面小字

**触发条件**：`setupAi === "cpu"` 且 `setupLevel === 4`（只有「极限」）。

**做法**（这是唯一能同时满足「不影响其他按键位置」和 browser-check 既有断言的写法）：

- 拉条 `#aiRange` 加 `transform: translateY(-5px)` 上移。`transform` **不参与布局**，所以行高、下面所有行的位置一个像素都不动。
- 小字 `#aiHint` 挂在 `#aiLevel` 下面，`position:absolute` + `left:50% / translateX(-50%)`，**完全脱离文档流**，同样零布局影响。
- 用 `#aiLevel[data-lv="4"]` 选，不新增 JS 状态：`data-lv` 已经由 `syncAiLevel` 维护（[index.html:9621](../../../Web_Gomoku3D/index.html#L9621)），少一处会漂移的地方。
- 没选人机时（拉条 `disabled` + `dim`）不显示、不上移——那时候这个提示没有意义。

**browser-check 的两条既有断言必须仍然通过**：
- `aiLevelRowH <= 48`（[browser-check.mjs:2182](../../../_verify/browser-check.mjs#L2182)）
- `|lvCenterOff| <= 1`（拉条水平居中偏差，[browser-check.mjs:2179](../../../_verify/browser-check.mjs#L2179)）——`translateY` 不动水平位置，安全。

## 四、必须守住的不变量

改这一块**不许**破坏下面任何一条（都有断言或注释钉着）：

1. **同局面 + 同种子 → 同一动作**。全项目唯一随机源是 `aiRng`，不许用 `Math.random`，不许用墙钟参与决策。置换表的代数戳重置是这条的一部分。
2. **能立刻赢就必须赢**（判断链第 1 步）。
3. **绝不主动走成长连自尽**（判断链第 2 步剔除 `LoseByOverline`）。
4. **对方下一步能赢就必须堵**（判断链第 3 步）。注意「对方是先手方且会走出六连 → 他反而判负」，那种点不进 `foeWin`。
5. **转动永远赢不了棋**（引擎整体回滚任何转出 ≥winLength 连线的转动），所以转动**绝不许**插到「能赢」和「必堵」前面。
6. **电脑挑的动作必须是引擎一定接受的**。转动判定只有 `_tryRotate` 一份实现，探针和真转共用——任何「照着写一遍过滤条件」的写法迟早漏改一处，症状是**偶发卡死**。
7. **绝不出抛**。任何守卫不成立都返回 `{kind:"none"}`；控制台一个字符都不许有（browser-check 硬断言）。
8. **深度一律奇数**。

## 五、测试与测量方案

### 5.1 新增的断言

1. **VCT 的正确性（最重要）**：算杀报出来的胜着**必须真的赢**。构造法：让 VCT 报一个胜着，然后由一个**穷举应手**的对手来防，防不住才算通过。假胜着是这次最大的风险。
2. **VCT 不许漏长连判负**：受限方的算杀链里出现长连时，那一支必须被判负而不是判胜。
3. **置换表不许破坏硬规则**（**注意：不是"开/关选出同一动作"**）。原稿写的是「开关置换表选出的动作必须逐字段相同」，**这条是错的，做不到也不该要求**：置换表会改变 α-β 的剪枝顺序，同分着法的 tie-break 本来就会跟着变；32 位键在 65536 槽里还有极小概率碰撞。要求它逐字段相同，等于要求置换表什么都不做。
   正确的三条是：
   - **确定性**（本工程既有契约）：同局面 + 同种子 + **同配置** → 同一动作。配置相同就够，不跨配置比。
   - **硬规则不破**：开了置换表之后，「能赢必赢 / 必堵必堵 / 绝不自尽」三条断言照旧全绿（复用既有的那几组测试）。
   - **碰撞不至于翻车**：把表槽数故意调到极小（例如 64 槽）跑一批固定局面，硬规则仍须全绿——这是碰撞压力测试。
4. **置换表在转动下不出错**：四维下转一手再转回来，键必须回到原值。这一条是有效的，保留。
5. **走法两段式：量化差异，不要求逐字段相同**（同样因为剪枝顺序影响 tie-break）。做法：同一批固定局面，预筛版与全量版各跑一遍，**统计选出动作不同的比例**，并各自用既有硬规则测试过一遍。不同比例高说明预筛真的在改决策 → 必须配对 A/B，棋力掉了就退回全量。
6. **既有转动不变量继续成立**：`selfPlayRotAudit` 那三条（转完不留活三 / 拆形真拆掉 / 调形真跨档）+ 转动比例上界 1/6。
7. **档位梯子**：`ultra > xhigh > high > medium > low`，阈值仍是 55%（配对、随机开局）。

### 5.2 配对 A/B 测量台

新增 `_verify/ai-ab.mjs`（Node，零依赖，和 `_verify/` 下其它脚本同一套写法）：

```
node _verify/ai-ab.mjs --mode 4d --size 8 --cooldown 3 --games 40 \
     --new <新版内核> --old <旧版内核>
```

- **旧版内核从 git 取**：`git show 4337e18:Web_Gomoku3D/index.html`。这样「新旧对拍」是真的两份内核，不是同一份代码换个参数。
- **配对**：第 2k 局与第 2k+1 局共享开局种子、只对调颜色。**对照组（旧 vs 旧）必须恰好 50.0%**，否则报「测量台坏了」而不是报胜率。
- 输出：胜 / 负 / 和、得分率、平均手数、转动次数。
- 报告口径：**四维 8³ 冷却 3 手为主**，三维 15³ 为辅（只要求不回归）。

### 5.3 既有检查

`bash _verify/run-all.sh` 九步全绿。第 6 步（`ai.test.mjs`）会明显变慢——极限档不再有墙钟上限，自对局那几组要按新的计数预算重新定阈值。

## 六、风险

| 风险 | 后果 | 对策 |
|---|---|---|
| **VCT 报假胜着** | 电脑主动走出一手送死棋，玩家一眼看得出 | 5.1 第 1 条：穷举应手验证；活三必须穷举对方应手，不许只试一个 |

| **预筛丢掉根节点之外的正确着法** | 棋力**下降**且无症状 | 根节点不筛；5.1 第 5 条量化差异；配对 A/B，掉了就退 |

## 八、下一位接手的人要看的：v3.0.0 是另一件事

用户同时提了 **v3.0.0：四维增加拓扑玩法** —— 立方体六个面贯通（周期性边界），棋盘形状不变，五子可以跨过边界相邻成线。**这是规则层改动，不在本规格范围内**，要单独走一遍设计 → 规格 → 计划。

现在只记两条**会影响 v3.0.0 的伏笔**，免得这边把路堵死：

1. **3.3 的热循环内联会被 v3.0.0 重做一遍。** `RuleEngine.countRun`、`aiThreatAt` 的滑窗、`aiCandidates` 的邻域遍历，全都要变成「按轴取模」而不是「越界即停」。所以 3.3 改完之后，**在注释里留一句「这里 v3.0.0 要加环绕分支」**，别让下一个人以为那是最优形态。
2. **`Board3D` 的 `getOrDefault` / `inBounds` 语义会分叉。** 环绕模式下"越界"不再是非法，而是"绕回去"。这个判断必须有唯一一处定义，否则渲染（画格线、算坐标）和规则会各绕各的。
3. **转动在环面上仍然成立**（整层置换和边界无关），但 `fullScan` 会把同一条跨边界的线**数很多遍**（同一个循环可以从 n 个起点出发），去重是必须的。
