# 三维五子棋（网页版）

**单文件、零依赖、原生 WebGL2**。原作者版本（Unity/C#）已删除，现在这里是唯一的实现。

两种对局模式，开局时选：

| 模式 | 说明 |
|---|---|
| **三维 · 经典**（默认） | 原来的玩法，一个字没改 |
| **四维 · 可转层** | 在三维棋盘上**像魔方一样转动某一层**，已经落下的棋子会跟着被搬走。"四维"指的是时间轴 —— 棋盘本身会变，坐标仍然是三维的 |

界面上三处值得单独说：

- **起始界面**：左侧是一张自动缓慢旋转的 10×10×10 演示棋盘，配色走古风（宣纸底、墨色字、朱砂点缀）。
- **棋盘尺寸可以自己填**：三维模式 x/y/z 三个数各自 8..50（默认三轴联动，关掉才能填长方体），四维模式填一个 N。
- **右上角「具体规则」**：点开是 `RULES_SPEC.md` **全文**（表格、代码、强调都渲染过），Esc 或点空白处关闭。

## 怎么跑

**直接双击 `index.html`** 就行。

不需要服务器、不需要联网、不需要 npm install。

### 为什么不引入 Three.js

常见做法是从 CDN 引 Three.js。这里刻意不引，有两个具体原因：

1. **`file://` 下的模块加载会被 CORS 拦掉。** 用 `<script type="module" src="./xxx.js">`
   的页面直接双击打开在 Chrome 里是白屏，必须在浏览器控制台里看到一串 CORS 报错 ——
   这是最容易让人以为"代码坏了"的一类问题。
2. 走 CDN 就必须联网。单文件自包含则拷到任何地方都能跑。

代价是自己写矩阵和实例化渲染。这部分大约 200 行，换来确定性，划算。

## 操作

按键与鼠标行为：

| 操作 | 效果 |
|---|---|
| 左侧按住左键拖拽 | 旋转立体棋盘 |
| 左侧滚轮 | 缩放 |
| 左侧单击 | 在当前层落子（位移 < 6 像素才算点击） |
| 左侧悬停 | **红线标出即将落子的格点所在的 x / y / z 三条贯穿线** |
| 右侧面板单击格子 | 落子 |
| 右侧面板单击缩略图 | 跳到那一层 |
| `<` `>` / `Q` `E` / `[` `]` | 切换当前层 |
| `Z` / `R` / `G` | 悔棋 / 重开 / 切换视图模式 |
| 右侧「转动一层」面板 | **仅四维模式**：选轴 / 层 / 方向 / 次数，点「执行转动」 |
| `T` / `Y` | **仅四维模式**：执行转动 / 恢复本次转动 |

**绿框 = 待转的那一层，蓝框 = 当前层。** 两者刻意是独立的选择：当前层是你要落子的层，待转层是你要转的层；
选 z 轴时它们可能恰好重合，那时绿框盖在蓝框上。不做同步是因为 x / y 轴的层和"当前层"根本不是同一个概念 ——
单向同步会在用户手选之后又被盖回去。

**松手之后棋盘完全静止** —— 没有惯性、没有阻尼、没有自动旋转。这是刻意的。

### 悬停校准线

鼠标在立体棋盘上移动时，即将落子的那个格点上会实时亮起**三条红线**：分别沿 x、y、z
方向贯穿整个立方体，也就是该格点所属的那三个轴向。

为什么是轴向而不是全部 13 个方向：透视下斜线至少有明显的走向，轴向线在密集的格网里
最难判断"我到底对准了哪一条"—— 而轴线恰恰是最容易被忽略的获胜方向（三维五子棋里，
光堵正面是没用的）。这三条线同时也是 13 个获胜方向中的 3 个，所以它既是落点校准，
也是"这一手会落在哪几条线上"的提示。

红线是 `#e02b20`，比 `--danger`(`#c0392b`) 亮：`--danger` 已经被"长连犯规"的获胜连线
占了，两者不会同时出现，但含义完全不同，颜色上必须能分开。

线宽取 `cs*0.09`，比静态格线（`cs*0.06`）粗 —— 必须压得住它盖住的那三条灰线，
否则"改成红色"会退化成"灰线上蒙了一层红雾"。

几何在 `Game.hoverLineSegments()` 里，**独立成方法是为了能被测试直接检查**：
三个方向是各写一遍下标的，写反一个分量在屏幕上只表现为"红线偏了一点"，
和"本来就这样"肉眼分不开，但校准功能就废了 —— 而那正是这个功能的全部意义。

## 规则

规则定义只有一份：[RULES_SPEC.md](RULES_SPEC.md)。它**是写给玩家的** ——
被原样嵌进 `index.html` 的「具体规则」浮层，测试断言两边**逐字节相等**（见下）。

### 规则实现细节（2026-09-25 从 RULES_SPEC.md 迁出）

那份文档的读者是玩家，所以把工程侧的内容挪到了这里。
下面这些是**内核里真实存在、但玩家够不到**的开关和判定顺序 ——
设置页只暴露四项：对局模式 / 谁先手 / 棋盘尺寸 / 转动冷却。

**`RuleSet` 上可改的开关：**

| 开关 | 默认 | 改了的后果 |
|---|---|---|
| `RestrictionTarget` | `FirstPlayer` | 长连判负**跟着先手走**。设成 `Black` 就是传统连珠的"永远由黑棋承担"；设成 `None` 则双方都不受限 |
| `OverlineLoses` | `true` | 设 `false` → 长连不再判负，退化成自由规则（双方 ≥5 连即胜） |
| `OverlineTakesPrecedence` | `true` | 一手同时踩中 5 连和长连时：`true` 判长连负，`false` 判恰好 5 连胜 |
| `WinLength` | `5` | 规则里的"5"都是它 |
| `RotationCooldownPlacements` | `5` | 两次转动之间至少要落的子数（UI 可调 3/5/8/10） |

**判定顺序有测试钉着。** 受限方沿一条直线连续落子时，第 5 颗就已经判胜、棋局立即结束，
根本走不到第 6 颗 —— 所以长连犯规**只可能由"一手把两段接起来"产生**（例如已有 `0,1,2` 和 `4,5`，
落在 `3` 上接成 6 连），不可能慢慢摆出来。测试 `Overline_StraightLineFiveWinsBeforeSixCanEverAppear`
就是钉这条的：谁要是"优化"成先查长连再查胜，行为会被改掉。

**悔棋是 O(1) 的。** 只清掉那一格的子，不需要重扫全盘 —— 依据是"棋局只可能在最后一步分出胜负"
（分出胜负后落子会被拒绝），所以撤掉最后一步之后，之前的局面必定是未分出胜负的。

**和局**实战中几乎不可能出现（15³ 有 3375 格），但必须处理，否则界面会永远停在"进行中"。
测试用 2³ 棋盘 + `WinLength = 3` 覆盖这条路径（2³ 里不存在长度 3 的连线）。

**四维模式的实现要点：**

- 转动合法性第 5 条（转完必须和转之前不同）按**状态比较**而不是按次数判定，
  它同时覆盖两种"转了等于没转"：该层是空的、或图案恰好在该旋转下不变。
  这两种要**分开提示**给玩家，否则按钮看起来就是坏的。
- 第 6 条（转完不得存在 ≥`WinLength` 的连线，否则整体回滚）是三种可能设计里最保守的一种：
  它不需要给 `RuleEngine` 增加任何新的胜负语义，既有的判胜 / 长连判负逻辑一个字都不用改。
  代价是转动不能当进攻手段用，只能拆对手的线、或调整自己的结构。
  一条前提：棋局还在进行中时，盘面上必定不存在 ≥`WinLength` 的极大连线（一旦出现，上一手
  `Place` 就已经把棋局判成结束了），所以"转完扫描到连线"等价于"这次转动造出了连线"，
  不需要额外的前后对比。测试 `Rotate_NeverDecidesTheGame` 与向量回放共同钉住它。
  公开资料里的相近玩法（Pentago 的转象限、Tic Tac Turn 的转层、RooTTT 的"转出对手的线判你负"）
  对"转动造出连线"的处理各不相同（判和局 / 判转动方负 / 判给自己），本实现选回滚。
- 撤销转动 = 顺时针再转 `4 − t` 次（`t` 是原转动次数），不需要额外存原图。
  冷却计数从历史推导，所以悔棋会自动把冷却一并回退，不存在"计数器和棋盘对不上"的第二份状态。
- **内核的尺寸下限：三维是 15，四维是 `max(2, WinLength)`。** UI 收得更紧（都从 8 起）是产品选择，
  不是规则。三维内核下限 15 是历史；四维放开下限的理由是：棋盘越大，一层里的棋子越少，
  转动越看不出来。实测量（200 局贪心模拟的中位数）：

| N | 一局中位手数 | 一局结束时一层里的平均子数 |
|---|---|---|
| 5 | 15 | 3.0 |
| 6 | 13 | 2.2 |
| 8 | 11 | 1.4 |
| 15 | 10 | 0.67 |

15³ 下一层里平均不到一颗子，多数转动会撞上"没有变化"，所以四维默认 8。
（5 / 6 两档是 UI 下限还是 5 的那一轮测的，现在选不到；数据留着是为了不丢记录。
同一个表也抄在 `index.html` 的 `fourDMeasured` 里。）

**没有实现的东西**（明确声明）：双三禁手、双四禁手、"禁手点"概念都没有 ——
本作的判罚是**落子之后的裁决**，不是"这个点不能落"。要加需要在 `RuleEngine.Judge` 里
增加形状识别，是独立的一块工作。转动没有动画（瞬时到位 + 高亮选中层），不能拖拽转动，
也没有 AI 对手。

**为什么默认要给先手加限制**：**事实** —— 平面 15×15 的自由规则五子棋本身已被证明是先手必胜
（Victor Allis, 1993），所以"理论上先手必胜"不是三维独有的问题。
**预测**（有强理论支撑，但不是事实）—— 三维里制造"一子双威胁"比平面容易一个数量级，
而对手一次只能堵一个点，所以先手的**实际**优势比平面大得多；面对不会造双威胁的对手，
大约 8～12 手就能锁定胜局。这就是默认规则要给先手加长连禁手的原因：关掉它，后手的体验会很差。

## 起始界面与演示棋盘

起始界面左侧那张 10×10×10 的棋盘是**装饰**，有三个刻意的决定：

1. **它和玩家那一局是两块不同的棋盘。** 在设置页里改尺寸、换模式时，玩家的棋局一个子都不该动，
   所以演示盘是一块独立的 `Board3D`，只被 `uploadPreviewInstances` 读。上面写着「演示棋盘」的铭牌
   也是为此：从对局里点「设置」进来时，左边仍然摆着一盘棋，不说明的话看起来像是自己的棋局还在。
2. **只换相机的字段，不换相机对象。** `drawPreview()` 做的是「存 → 换成演示值 → 画 → 还原」。
   对局视图「松手之后棋盘完全静止」是刻意保留的（见上面的「操作」一节），
   所以自动旋转**只对起始界面放开** —— 漏还一个相机字段，对局的取景就会被起始界面改掉，
   而那种偏差很难看出来源。测试里逐字段断言了这一点。
3. **绘制复用同一个 `draw3D()`**，没有第二套绘制代码。把逐实例数据换成演示盘的、
   把光标 / 悬停线 / 待转层 / 获胜线全部清成 0，`draw3D` 是数据驱动的，画出来自然是对的。
   代价是演示盘上没有「当前层」蓝框 —— 那东西的含义是「这一手要落在哪一层」，
   而起始界面根本没有「这一手」。

演示盘上的棋子由**固定种子的整数哈希**散布（64 个位置），所以刷新页面看到的局面完全一样。
用 `Math.random` 的话每次刷新布局都变，看起来像 bug，也没法拿它当"换个配色好不好看"的基准。
**它不是一局合法的棋** —— 有重复落子、也可能凑巧连成 5 个，它从来不经过 `RuleEngine`。

### 棋子为什么聚在中间

一开始是均匀撒满整盘的，看起来像"随便扔上去的"。现在每个轴的坐标取 `PREVIEW_BIAS` 个
独立均匀值的平均 —— 平均值按中心极限向棋盘正中收，得到中间密、边缘疏的一团。

| BIAS | 包围盒 | 三轴 sd |
|---|---|---|
| 1（均匀） | 10×10×10 | 2.61 |
| 3 | 7×7×8 | 1.48 |
| **5（默认）** | **6×7×7** | **1.40** |
| 6 | 6×6×6 | 1.37 |
| 8 | 6×6×6 | 1.41（且只剩 46 颗） |

**5 之后基本到顶**：格坐标是整数，再平均只会被 `Math.round` 量化掉，收紧的收益全被
"撞位丢子"吃掉。有用区间 1..7。

用"平均 k 个均匀值"而不是"直接缩小取值范围"：后者会把棋子填满一个小立方体、
边界上出现一条明显的直边，看起来像整个棋盘被裁小了；取平均得到的团没有那条边。

**这里踩过一个坑，值得记下来**：种子表最初只有 3 行 3 列，而 BIAS 是旋钮。
BIAS>3 时 `salts[k]` 是 `undefined`，`Math.imul(x, undefined)` 得 0，
"取平均"就变成"往 0 那一侧拽"—— 棋子在屏幕上整团偏到角落。
默认值 3 恰好在表内，所以只测默认值是**测不出来**的，只有把旋钮调大才看得见。
现在表长 8、越界直接抛异常，`dom-smoke.test.mjs` 里那条
"跨多档取值都必须居中、且越大越紧"就是为了钉住它（注入验证确认过：去掉越界检查会报错）。

自转是**时间驱动**的（6 度/秒，一圈 60 秒），不是每帧固定增量：后者在 144Hz 屏上会转得比 60Hz 快一倍多。
`dt` 被夹在 `[0, 0.2]` 秒内 —— 上限给"切回标签页"用（几十秒的 dt 会让棋盘唰地跳一大截），
下限给负 dt 用（时钟回拨会让角度倒着走，而"棋盘偶尔倒转一下"是最难归因的那类现象）。

## 长方体棋盘（网页版独有的扩展）

三维模式的三个轴可以填成不等长（例如 8×12×30）。**这件事没有 C# 对应物**，
所以它的证据边界必须说清楚：

| | 立方路径 | 长方体路径 |
|---|---|---|
| 实现 | 与 C# `Board3D` 逐条对应 | 网页版独有 |
| 证据 | `vectors.json`（C# 导出）+ `rules.test.mjs` 11733 项 | `dims.test.mjs` 98 项，仅此一份 |
| `GameSession.create(n, …)` | 一个数字，与原实现逐字节一致 | 传 `[x,y,z]` |

立方路径刻意走「一个数字」这一支：向量回放全部用数字构造，所以那条路一个字节都没变，
**"两份实现一致"的既有证据依然原样成立**。长方体是在它旁边新开的一条路，而不是把原来的路改宽。

### 四维模式为什么必须立方（不是"没做"）

转一层的置换是 `(u, v) → (v, (n−1)−u)`。设该层的两条自由轴边长为 `nu`、`nv`：

- 结果要落在原盒子里，`v' = n−1−u` 要求 `nv ≥ nu`；
- 同时 `u' = v` 要求 `nu ≥ nv`；

**故 `nu = nv`。** 三个轴都要能转 ⇒ `nx = ny = nz`。所以长方体上的转层不是"还没实现"，
是根本不存在这个操作。代码里两处强制：`Board3D.requireCube()`（`layerIndex` / `countLayerStones` /
`rotateLayer` 的第一步）和 `FourDSession.rotate()` 的守卫（返回 `Rejected` + 一句能读懂的原因，
而不是抛异常 —— 和层号越界、冷却未到同类：棋盘不动、不消耗回合）。

UI 上四维模式只给一个 N，切模式时强制立方；`newGame` 里再兜一次底，
免得出现"开局成功、但一颗子都转不动"这种只能靠点按钮才发现的坏状态。

### 一个容易写错的地方

格距 `cs` 对**三个轴取同一个值**（`cellSize()` 取最长边归一化到 10 个世界单位）。
不能每个轴各用各的：球体网格是各向同性缩放（`aPos * w`），三个轴用不同格距就只能是椭球。
取最长边而不是最短边，是为了让长方体的长边正好卡在原来的取景框里 ——
视线下轮廓的半宽最大是 √2·10/2 ≈ 7.07，而 `frameBoard` 的取景半径是 10·0.5·1.45 = 7.25，
所以相机参数一个都不用动。

## 配色：单一事实源

颜色原来散在**五个地方**：CSS 变量一套、`gl.clearColor` 一套、着色器常量 `STONE_EDGE` 一套、
两块 canvas 各一套，而且大多是裸写的十六进制。换主题时漏掉任何一处，就会出现
「三维视图和面板不是同一个色」—— 这种偏差在屏幕上只表现为"好像有点不一样"，很难定位。

现在唯一事实源是 CSS 的 `:root`，JS 侧只解析一次（`Palette`）；读不到 CSS（node 桩、老浏览器）
时退回 `FALLBACK_COLORS`，并**由 `dom-smoke.test.mjs` 断言兜底表与 CSS 实际值逐条一致**。
`Palette.rgb()` 只认 `#rrggbb`，遇到别的写法直接抛 —— 静默变成黑色比报错难查得多。

顺带修掉的一处漂移：三维视图里的白子原来是纯白 `[1,1,1]`，而二维面板用的是 `--white`（`#fdfaf2`），
两者其实不是一个颜色。现在都走 `--white`。

## 规则全文：为什么它是生成的

右上角那个「具体规则」显示的是 [RULES_SPEC.md](RULES_SPEC.md) 的**全文**，
一字不改。它的实现方式值得说明，因为"把文档塞进页面"有两种做法，只有一种是对的：

| | 手抄一份进 HTML | 由脚本从源文件生成（**现在这样**） |
|---|---|---|
| 正文份数 | 2 份 | 1 份 |
| 改了 RULES_SPEC.md | 页面照旧显示旧规则，**没有任何东西会报警** | `node _verify/embed-rules.mjs` 重新生成；忘了跑，测试直接红 |
| 玩家看到的规则 | 可能和代码执行的规则不一致 | 恒等于权威定义 |

那个"两份文本悄悄分叉"的坑这个工程已经踩过一次（颜色散在五处、`worldOf` 有两份拷贝），
所以这里从一开始就用生成 + 断言的写法：

- `_verify/embed-rules.mjs` —— 把 `RULES_SPEC.md` 写进 `index.html` 的
  `<script type="text/plain" id="rulesSrc">` 里。用 `text/plain` 而不是 JS 字符串：
  反引号、`${}`、反斜杠都不需要转义，浏览器把它当纯文本存着，页面读 `.textContent` 就行。
- `tests/dom-smoke.test.mjs` 断言**页面里那段逐字节等于源文件**，不一致时报出第一处差在哪一行。
- `_verify/run-all.sh` 第 1 步跑 `embed-rules.mjs --check`，改了文档忘了重新生成会当场失败。

**为什么不做 Markdown 库**：单文件零依赖是这个页面的前提（`file://` 下连
`<script type="module">` 都会被 CORS 拦掉）。所以手写了一个约 70 行的子集渲染器，
只覆盖这份文档实际用到的构造：标题 / 表格 / 无序列表 / 引用 / 分隔线 / 行内 code / 粗体。

写这个渲染器踩了两个坑，都被测试抓出来了，记在这里免得下次再犯：

1. **转义和结构判断的先后**。分块靠行首记号（`#` `|` `-` `>` `---`），而 `>` 转义后是 `&gt;`
   —— "先整体转义、再按行首匹配"会让**引用块永远匹配不上**，全变成普通段落。
   正确顺序是：用未转义的行判结构 → 取出内容 → 再"先转义、后插行内标签"。
2. **行内 code 要先切开，不能两遍 replace**。先把 `` `x**y**z` `` 换成 `<code>...</code>`，
   第二遍的粗体规则照样会命中 code 里的 `**y**` —— 换标签并没有把里面的文字保护起来。
   正确做法是按 code span 切开，只对 code 之外的部分做行内替换。
   （这一条对**当前这份文档**其实不会触发：`RULES_SPEC.md` 里没有 code span 含 `**`。
   是测试用构造样例把潜在错误逼出来的。）

另外，规则浮层开着时**所有快捷键都失效**（只有 Esc 有效）。不这么做的话，
"看规则时按了下 R 把棋局重开了"是必然会发生的事，而屏幕上唯一可见的是规则，
玩家根本不会想到是自己按的。

三维拾取、事件回调挂载，以及四维模式的：面板随模式显隐、冷却门槛、恢复本次转动、
空层提示、待转层绿框的几何、转动后最后一手光晕不挂在无关格子上。

这个桩有两处是刻意设计的，否则它会退化成"什么都放行"：

- `document.getElementById` 只对 `index.html` 里**真实存在**的 id 返回元素，其余返回 `null`。
  这样 `el` 列表里任何拼错的 id 都会立刻变成空引用。
- 面板点击的坐标换算做了**往返验证**：给定格子 → 算出屏幕坐标 → 再换算回格子，
  必须完全一致（含四角）。这条能抓住三维视图与二维面板之间的坐标约定写反
  （比如 y 轴方向不一致）这类最难靠肉眼发现的 bug。围绕同一处坐标约定还压了另外两条：
  **偏着点必须命中最近的交织点**（专盯 `floor` 算格子再当格点用，会整体偏半格），
  以及**最外圈线之外一格外必须落空**（命中区只能向外扩半格，不能整块画布都有响应）。
- 三维格线的**顶点数按公式校验**：必须是 `(3n² + 12) × 12` —— 三个方向各 n² 条线，
  加上外框 12 条棱，每条线 12 个顶点。少写一个方向（或把某个循环的边界写错）
  会立刻变成数字不符，不必等肉眼去看。15³ 和 50³ 各验一次。
- 悬停校准线校验**几何本身**而不只是"传了数据"：三条线必须都穿过将要落子的那个格点，
  每条只能沿一个轴延伸，且三个方向必须 x/y/z 各一条。还验了没悬停、已分胜负两种情况下
  一条都不该有。这两条断言都做过**注入验证**（把 z 向线的 y 坐标改成 z、把 x 向线改成斜线，
  测试分别报"在第 1 维上不含格点"和"校准线不是轴向的"），确认它们抓得住错。
- 待转层绿框（`rotationOutlineSegments`）同样校验**几何本身**：三条轴 × 三个层，4 条边
  都必须落在该轴该层的平面上、端头都收在 ±ext、且 2 条沿一个自由轴 + 2 条沿另一个。
  这一条盯的是"三个轴的自由轴顺序各写一遍下标"里写反分量的错法 —— 那种错在屏幕上
  只表现为绿框跑到了另一个平面上。
- 转动之后，最后一手光晕必须只挂在"那颗子还在原地"的格子上。四维模式下转动会把棋子搬走，
  原来的实现只判"那一格不空"，于是光晕会挂到空格或被对手顶上来的格子上。
  这条测试用一次真实的转动把它钉死。

这一节记录的是**当初**网页版怎么从 Unity 版对应过来的。Unity/C# 实现已经删除，
所以左边那一列指向的文件都不存在了 —— 保留它只是为了留住"右边为什么长这样"的设计理由，
**不是**让你去找那些文件。

| Unity（已删除） | 网页版 | 说明 |
|---|---|---|
| `Core/Board3D.cs` | `Board3D` 类 | 扁平 `Uint8Array`，索引 `x + n*(y + n*z)`，x 最快维使一层在内存里连续 |
| `Core/RuleEngine.cs` | `RuleEngine` 对象 | `judge`（增量，O(1)）+ `fullScan`（全盘，独立实现） |
| `Core/GameSession.cs` | `GameSession` 类 | 同样的悔棋 O(1) 论证、同样的规则快照语义 |
| `Core/RuleSet.cs` | `RuleSet` 类 | 同样的长连优先级与绑定目标 |
| `Core/Rotation.cs` | `RotationOps` / `RotationMove` | **四维**：转动置换 `(u,v) → (v,(n−1)−u)`、顺时针次数归一化。两条边都是公开 API，测试直接钉坐标 |
| `Core/FourDSession.cs` | `FourDSession` 类 | **四维**：包在 `GameSession` 外面。冷却 / 空层判定 / 连线回滚 / 转动时间线 / 恢复本次转动。三维模式下是透明壳 |
| `BoardView3D.cs` + 着色器 | `Renderer` + GLSL | 逐实例属性传颜色。幽灵子用标准 alpha 混合（**不是**加性混合 —— 浅灰底上加法只会越加越白，见 `draw3D` 里的 `blendFunc`） |
| `MeshFactory.LineMeshBuilder` | `Renderer.buildLines` | 同样的"十字四边形"方案给线段厚度 |
| `LayerPanelGraphics.cs` | `drawLayerBase` / `drawLayerOverlay` | 同样拆成"静态层 + 悬停层"两个缓冲，避免鼠标移动时重绘几千个格子 |
| `LayerStripGraphic` | `drawStrip` | 同样的按容器宽高比决定列数、同样在棋子过多时退化成占用条 |
| `OrbitCameraRig.cs` | `OrbitCamera` | 同样的球坐标、同样的 `frameBoard` 取景公式 |

**规则内核上新增的一处分叉**（除它之外逐条一致）：

`Board3D` / `GameSession` 现在接受 `[nx, ny, nz]`，`RuleEngine.fullScan`、`countColumnStones`、
渲染层的 `cellSize` / `worldOf` / `gridSegments` 都按三条边各算一份。立方时全部退化成原来的写法
（`index = x + n*(y + n*z)`、`cs = 10/n`、`3n²+12` 条格线），这一点由 `dims.test.mjs` 与
既有向量双重钉住。**C# 侧只有一个 `Size`，没有对应实现** —— 见上面的「长方体棋盘」一节。

另外三类"同一件事写两遍"的重复被合并了（都是这次改动顺手清掉的，属于安全重构）：

1. `worldOf` 与 `worldOfLocal` 是同一个公式的两份拷贝 —— 合成一个 `worldOf(x,y,z,dims,cs)`。
   棋盘有三条不同边长之后，这种重复直接变成错误来源（三个轴各要一个偏移）。
2. 颜色散在五处 → 收敛到 `Palette`（见上面的「配色：单一事实源」）。
3. `init()` 里那段"准备好起始界面"的代码 → 直接调 `openSetup()`，
   否则"页面刚打开"和"从对局点设置进来"这两条路径可以有细微差别。

**渲染上网页版自己的三处做法**（这几处只是和原 Unity 版的画法不同，与规则无关）：

1. **三维格线**：这一版画的是完整的三维格 —— x/y/z 三个方向各 n² 条贯穿线（50³ 是 7500 条）。
   原 Unity 版当时只有当前层的平面格线加四条角落深度导轨。
2. **二维面板 / 缩略图的落子点**：这一版落在**线的交织点**上，原 Unity 版是格心。
   两者与三维视图的约定也因此不同（三维那边本来就是格点）。
3. **悬停校准线**：这一版悬停时会用红线标出落点所属的三条轴向贯穿线。
   原 Unity 版当时没有这个功能。

### 三处刻意的差异

1. **二维面板用 Canvas 2D 而不是 DOM 网格。** 50×50 一层是 2500 个格子，
   用 DOM 就是 2500 个节点，每次重绘都要走一遍样式计算和布局。
   Canvas 2D 的 `fillRect` 直接画到像素缓冲，量级完全不同。
   （这也是 Unity 版里必须自绘 `MaskableGraphic` 而不是用 `GridLayoutGroup` 的同一个理由。）
2. **y 轴方向。** 面板 canvas 用 `ctx.setTransform(dpr, 0, 0, -dpr, 0, h)` 把 y 翻成向上 ——
   这样面板的坐标语义就和"从 −z 正视第 k 层"完全一致，和三维世界同向。
   缩略条反过来保持 canvas 默认的 y 向下，并在画棋子时把 y 翻回去。
   这两处不一致是**刻意**的（各自匹配其用途），改动前请先看 `drawStrip` 里的注释。
3. **面板画的是"线"而不是"格"。** n×n 个**交织点**，相邻两点间距 `cs = min(w,h)/n`，
   整盘跨度 `(n-1)*cs`，板面再往每边多铺 `cs/2`（真实棋盘的板边就是这样）。
   棋子、最后一手圈、获胜连线、悬停框、星位**全部**按交织点定位 ——
   这一套坐标在 `drawLayerBase` / `drawLayerOverlay` / `cellFromEvent` 三处各算一遍，
   改任何一处都必须同时改另外两处，`dom-smoke.test.mjs` 里那三条坐标断言就是为了兜住它。
   历史教训：**改之前面板用的是格心（`(x+0.5)*cs`）、三维用的是格点，两边差半格错了很久**
   —— 三维那边一直是对的，只有面板不对，而肉眼很难同时盯着两个视图看出半格偏差。

## 已知限制

| 限制 | 说明 |
|---|---|
| 逐实例数据每次变化整体重算 | O(n³)，50³ 是 125,000 次迭代，约几百微秒。比维护增量状态可靠得多。 |
| 缩略图在棋子很多时退化 | 超过 4000 颗时只显示每层占用条。 |
| 拾取退化为"射线 × 当前层平面" | 原 Unity 版也是这个做法。正好侧视当前层时（射线与平面平行）无法判断深度，此时不做拾取。 |
| 三维格线没有深度感（**从 15³ 起就成立**，不是大棋盘才有） | 视线穿过立方体会叠上 n 层**屏幕位置完全重合**的平行格线，而格线是 alpha 混合画的，累积剩余透过率是 `0.45^n`：n=10 → 3.4e-4，n=15 → 6.3e-6，已经饱和。所以内部会读成一片灰网，而不是"近处清楚、远处淡"；n 变大只是让网更密。这是叠同位置图元的固有问题，**调 alpha 只能整体变淡、消不掉**。想要深度感得把 `draw3D` 里的 `depthMask(false)` 改成 `true`，代价是视线正对轴向时几乎看不见内部。 |
| 没有 AI / 存档 | 需求里只要有同人对战。 |
| 长方体下 `board.size` 会抛异常 | 这是**刻意**的：返回 `nx` 会让"只改了三个轴里的一个"这类漏改静默地用一个错的数继续跑。需要尺寸的地方一律用 `dims` / `nx` / `ny` / `nz`。这次改动中它已经抓到过一处漏改（`refreshTexts`）。 |
| 起始界面的演示盘是装饰 | 不是一局合法的棋，也不经过规则内核；它和玩家的棋局是两块不同的 `Board3D`。 |
| 从对局中点「设置」再点「开始游戏」会重开一局 | 原有行为，没有改。左边现在摆着演示盘，铭牌就是为此加的；但"棋局会被丢掉"这一点本身没有变，想要"改完设置继续下"需要另外做。 |
