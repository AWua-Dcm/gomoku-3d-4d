# 注入验证

**结论**：这个仓库有两个"先把代码改坏、再看检查会不会红"的脚本——`inject-rulenote.py`（改坏起始界面的规则摘要 3 处）、`inject-i18n.py`（弄坏语言切换的几条通路共 8 处：漏翻静态/动态/内核文案、切回中文失效、列表不高亮、复数不选形……）。

**为什么存在**：**证不了会红的检查等于没测。** 一个断言如果永远绿，它和不存在没有区别——注入验证就是每套关键检查的"负向证明"，逐条写明"这处坏掉该由哪条检查抓到"。

**规矩**（这套脚本自己的工作纪律）：

- 这两个脚本会临时改坏 `index.html` 再还原（`finally` 里恢复）；
- 它们跑 browser-check 时**写临时目录**，绝不碰 `_verify/shots/` 那批基线图——截图是在报告失败之前拍的，走默认目录的话每注入一次就把故意弄坏的页面写进版本库，`git status` 从此分不清"图被弄脏了"和"界面真的改了"；
- 新增断言时的对应动作：**把这个断言保护的东西改坏一次**，确认它会红（v3.1.7 新加的两条内核断言就是这么验的）。
