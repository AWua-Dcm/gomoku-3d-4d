# 转出线不等于赢

**结论**：`RotateOutcome` 的 `accepted && lines > 0` 只说明"这一转造出了线"，**不说明转动方赢了** —— 受限方（先手）转出的是 6+ 连长连时，`decideByRotation` 会当场判长连负。AI 的"转动能赢就转"硬规则（第 1b 步）原来只看 `lines > 0`，于是**先手电脑会主动转出自己的长连、当场判负** —— 转的是自己，输的也是自己。

**实测复现（2026-10-14）**：8³ 上黑（先手）两段 z 向三连（z=1..3 与 z=5..7）＋散子 (7,0,4)，绕 z 轴第 4 层顺时针转 1 次把两段接成 7 连。修复前 `aiChooseMove(medium, seed=8)` 正好返回这一转；执行后 `Rotated` → `Decided` → 胜者 = 白 → `LoseByOverline`。

**修法**：第 1b 步探到的每条线按 `decideByRotation` 的优先级分"赢 / 自尽"：`hasOver && 受限方 && (precedence || 无恰好 5)` → 记进 `rotLoses`，不返回；第 6 步三个采用点（rotAll / rotCand / build 的二次探针）也排除。**判定口径与 `decideByRotation` 逐条对齐** —— 别在一边"照着写一遍"，两处一起改才永远一致。

**边界**：

- 线的长度从 `_tryRotate` 那次扫描顺手带出（`lineLengths`）—— AI 段不许出现全盘扫描（源码级红线）。
- **潜在缝隙**：`rotLoses` 只覆盖第 1b 步探过的前 30 个候选（`AI_ROT_WIN_PROBE`）。现状没有档位开 `rotSearch`（rotAll 是死路）、各档 `rotProbe ≤ 14`，所以够用；若将来恢复 `rotSearch` 或把某档 `rotProbe` 调过 30，采用点会漏掉没探过的候选（复核时记录在案）。
- 规则本身一个字没改：玩家想这么输随他，引擎照样接受（测试里"前提"那条断言钉着）。

**证据**：`ai.test.mjs` 2b2 组（修复前红：`{"kind":"rotate","axis":2,"layer":4,"turns":1}`）。
